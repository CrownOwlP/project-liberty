# Development artwork fixtures (PW-0302)

## What these files are

Six PNG posters, one for each of the six fictional works in
`apps/web/src/lib/demo-catalog.ts`, produced by
`generate-fixture-artwork.mjs` in this directory. Each one is a smooth
two-colour gradient whose hue is a hash of its own asset reference. There is no
photograph in them, no typography, no logo and no likeness. Re-running the
generator reproduces them byte for byte.

## What these files are not

**They are not this product's artwork, and nothing may present them as such.**
Project Liberty has no licensed metadata or artwork provider: `PL-0302` and
`PL-0602` are BLOCKED on exactly that, and this directory does not change it.
These images exist so that the artwork path — the opaque reference in the
catalog contract, the resolution boundary at `GET /api/v1/artwork/{assetRef}`,
and the poster on the browse card — can be exercised from end to end on a
machine with no provider, instead of being typed and never run.

They are also not third-party material under any reading. The six works are
original to this repository, which is why `demo-catalog.ts` can state an `owned`
basis with a `null` register reference and have that be true rather than assumed;
the images are generated by a committed program in this repository, so the same
statement is true of them.

## The rights basis these carry

`owned`, with no register reference, matching the works they illustrate.
`@liberty/contracts/shared/artwork` requires every artwork reference to state a
basis and does not allow the undeclared case, for the reason that module records:
a work with an undeclared basis is refused from browse and nothing is published,
whereas an image with an undeclared basis that reached a page would be somebody
else's file served from our origin.

## Using them

The artwork boundary reads one operator-configured directory and refuses a
relative path, because `next dev`, a standalone `next start` and the desktop
sidecar each run from a different working directory and the same relative
setting would name three different places on three machines. So point the
variable at this directory with an absolute path:

```bash
# from the repository root
LIBERTY_ARTWORK_STORE="$PWD/apps/web/fixtures/artwork" npm run dev --workspace apps/web
```

```powershell
# Windows
$env:LIBERTY_ARTWORK_STORE = "D:\project-liberty\apps\web\fixtures\artwork"
```

With the variable unset the boundary answers `artwork_store_not_configured` and
every card falls back to its designed CSS gradient. That is a complete state, not
a broken one — the fallback is the same element the card rendered before PW-0302
— so a checkout with no artwork configured is the previous design intact rather
than a degraded version of this one.

The demo catalog itself is gated to non-deployment runtimes
(`demo-catalog.ts` explains why at length), so these fixtures cannot become the
catalog of a hosted build. Nothing gates this directory, because a directory of
generated gradients is not a rights claim; what it illustrates is.

## Regenerating

```bash
node apps/web/fixtures/artwork/generate-fixture-artwork.mjs
```

Change `WIDTH` or `HEIGHT` there and the `width`/`height` on the references in
`demo-catalog.ts` must change with them. The contract requires a reference to
state its asset's intrinsic size, and a reference that states the wrong one is
worse than one that states none: it reserves the wrong box and the page settles
into a different layout once the bytes arrive.
